# City Insight Map · Енергія

Прототип для **Poltava Open Data Hackathon 1.0**, трек 2 «Енергетичний менеджмент та енергетична стійкість».

**Енергонезалежність 311 комунальних будівель Полтавської громади: електроенергія, сонце, акумулятори.**
Внутрішній інструмент енергоменеджера. В одному вікні видно, скільки закладів можуть працювати на власному сонці й акумуляторах, скільки годин протримається заклад без світла і де за наявний бюджет поставити нові сонячні станції (СЕС).

> Демо: https://pl.mindal1ka.com — **тестовий вхід** (будь-яке ПІБ із двох слів і будь-який пароль). Станції, акумулятори й телеметрія там — **ДЕМО-ДАНІ**.
> Клас A–G і рекомендації щодо СЕС — **аналітична оцінка**, а не енергосертифікат і не проєкт станції.

## 1. Проблема → користувач → рішення → дані

**Проблема.** Під час відключень школа чи лікарня або має власну енергію, або ні. Місто цього не бачить:
- генерацію СЕС енергоменеджер дивиться, «заходячи в кожен об'єкт окремо»; спільної картини по станціях і акумуляторах немає;
- сонце зараз покриває **максимум ~30 %** власного споживання закладу, а надлишок **не можна продати** (законодавчо), тож станцію треба підбирати під власне споживання;
- дані UMUNI ніхто не перевіряє: 828 дефектів і аномалій на 300 з 311 будівель;
- ліміти ставлять «три останні роки + відсоток на тариф», без моніторингу.

Джерело: ТЗ треку 2 та інтерв'ю з енергоменеджером громади 19.11.2026.

**Користувач.** Енергоменеджер громади (через нього проходять 311 об'єктів UMUNI). Далі — департаменти освіти й охорони здоров'я та УЖКГ, керівники закладів (лише свій заклад).

**Рішення.**
| Що робить | Сторінка | Дані |
|---|---|---|
| Усі об'єкти: генерація, споживання, баланс «+ / −» до кінця дня, перемикач **«Зараз / Літній день»** | `/` | UMUNI + ДЕМО-телеметрія |
| Картка об'єкта: станція, акумулятор, погодинний графік, ліміти, **симулятор відключення** («скільки годин протримається») | `/object/{id}` | UMUNI + ДЕМО |
| **Рейтинг енергонезалежності** 0–100: частка самозабезпечення, години автономії, рекомендації | `/independence` | UMUNI + ДЕМО (див. стан нижче) |
| **Де ставити нові СЕС**: розмір під власне споживання, покриття, окупність, рейтинг; програма за бюджетом | `/solar`, `/solar/{id}` | **реальні**: UMUNI + PVGIS |
| Прогноз сонця на завтра (кВт·год на 1 кВт станції) | картка об'єкта / `/solar` | **реальні**: Open-Meteo + PVGIS |
| Якість даних: валідатор, аномалії, `data-defects.csv` | `/defects` | **реальні**: UMUNI |
| Рейтинг будівель і клас A–G у межах категорії | `/rating`, `/building/{id}` | **реальні**: UMUNI |
| Оновлення даних без розробника (XLSX з UMUNI) | `/upload` | — |

**Дані.** Пакет треку (UMUNI: реєстр 311 будівель, річне споживання 2025 і 2026), PVGIS, Open-Meteo. Деталі — розділ 3.

## 4. Архітектура

```
 XLSX UMUNI ──┬─ backend/data/*.xlsx (при старті)
              └─ POST /api/upload («Оновити дані»)
                        │
 import_umuni.py   тип звіту за заголовками; рік і дата — з аркуша «Інформація»
 analytics.py      МВт·год, кВт·год/м², медіани, класи A–G, рейтинг, валідатор
 solar.py          PVGIS → дах, генерація, розмір під власне споживання, окупність
 sites.py          ДЕМО: реєстр станцій, погодинний баланс, акумулятор, ліміти
 independence.py   індекс енергонезалежності, автономія, симуляція відключення (ДЕМО)
 forecast.py       Open-Meteo → прогноз генерації на 1–7 днів, запасний PVGIS
                        │
 main.py (FastAPI) ── /api/* (JSON, CSV) + роздає зібраний фронтенд
                        │
 frontend/ (SvelteKit SPA, adapter-static)
```

Один процес, один порт (8000). Дані в пам'яті, перераховуються після кожного завантаження.

| Метод | Що повертає |
|---|---|
| `GET /api/summary` | роки, охоплення, медіани категорій, класи, кількість дефектів |
| `GET /api/buildings`, `/api/buildings/{id}` | будівлі з класом, місцем у рейтингу або причиною виключення |
| `GET /api/defects`, `/api/defects.csv` | дефекти даних (CSV = `data-defects.csv`) |
| `POST /api/upload` | нове вивантаження UMUNI (XLSX) → перерахунок |
| `GET /api/solar`, `/api/solar/{id}` | рейтинг нових СЕС; параметри `?tariff=&capex=&fixed=&category=` |
| `GET /api/sites`, `/api/sites/{id}` | ДЕМО: об'єкти, станції, погодинний баланс; `?day=РРРР-ММ-ДД&hour=Г` — інший момент |
| `GET /api/independence`, `/api/independence/{id}` | ДЕМО: індекс 0–100, самозабезпечення, автономія, рекомендації, підсумок громади |
| `GET /api/sites/{id}/outage?start_hour=&hours=&soc=` | ДЕМО: погодинна симуляція відключення |
| `GET /api/forecast?days=1..7` | прогноз генерації на 1 кВт (Open-Meteo, кеш 1 год, запасний PVGIS) |

Інтерактивна документація API: `http://localhost:8000/docs`.

## 5. Підключення інверторів (Ф2.2-08): план інтеграції Deye Cloud

Зараз телеметрію генерує `sites.py`. Справжнє джерело підключається без зміни інтерфейсу:
1. **Реєстр станцій** `backend/data/ses_registry.csv` (колонки: `building_id, назва, адреса, панелей_шт, потужність_панелі_Вт, інвертор_модель, інвертор_кВт, акумулятор_кВт·год, акумулятор_кВт, приєднана_потужність_кВт, дата_запуску, джерело`). Якщо файл є, ДЕМО-реєстр не генерується.
2. **Колектор Deye Cloud** (OpenAPI, затримка даних ~1 хв за словами енергоменеджера): раз на 5 хв читає потужність PV, навантаження, мережу, SoC акумулятора кожної станції; зберігає в SQLite / TimescaleDB. Токен — лише в `.env` на сервері.
3. **Адаптери** LuxPower і Growatt з тим самим форматом (`hour, gen_kwh, cons_kwh, soc_pct`), що й зараз повертає `simulate_day`.
4. **План-факт** (Ф2.2-07): «план» — PVGIS × погода Open-Meteo, «факт» — інвертор; відхилення > 20 % три дні поспіль → сигнал «перевірити станцію».

Потрібно від міста: доступ до Deye Cloud (хоча б тестовий), перелік станцій, приєднана потужність будівель.

## 6. Запуск

### Docker Compose (рекомендовано, ~5 хв)
```bash
docker compose up --build
```
Відкрити http://localhost:8000. Вхід тестовий: будь-яке ПІБ (щонайменше 2 слова) і будь-який пароль. Папка `backend/data` підключена як том, тож завантажені файли зберігаються між перезапусками.

### Локально для розробки
Потрібні Python 3.12+ і Node.js 22.

```bash
# бекенд
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows; у Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --port 8000
```
```bash
# фронтенд (в іншому терміналі)
cd frontend
npm ci
npm run dev                     # http://localhost:5173, API — на :8000
```
Щоб побачити зібрану версію без Docker: `npm run build` у `frontend/`, після чого бекенд сам роздає її на http://localhost:8000.

Тести: `cd backend && python -m pytest`.

## 7. Як оновити дані

Без розробника, без ручної переробки файлу:
1. **«Оновити дані»** в інтерфейсі → XLSX з UMUNI («Характеристики будівель» або «Річний звіт використання ресурсів по будівлях»). Через API: `curl -F "file=@звіт.xlsx" http://localhost:8000/api/upload`.
2. **Або** покласти XLSX у `backend/data/` і перезапустити сервер.

Тип звіту визначається за заголовками, рік і дата — з аркуша «Інформація». Якщо за один рік є кілька файлів, береться новіший. Усе перераховується автоматично.

**`data-defects.csv`** формує сам застосунок (`GET /api/defects.csv`, кнопка в інтерфейсі). Колонки: тип, набір, будівля_id, будівля, поле, значення, правило, що_робити.
```bash
curl -o data-defects.csv http://localhost:8000/api/defects.csv
```

## 8. Безпека й етика

- **Лише внутрішній інструмент.** Дані про те, який заклад скільки годин протримається без світла, чутливі під час війни. Публічної карти резервного живлення немає і не буде.
- **Вхід зараз тестовий** (ПІБ і пароль не перевіряються, користувач живе лише у вкладці браузера). Публічне демо працює **тільки на ДЕМО-даних** станцій і акумуляторів. **Перш ніж завантажувати справжній реєстр станцій чи телеметрію, сайт має отримати справжню автентифікацію**: серверні сесії, ролі (енергоменеджер / департамент / заклад), доступ лише з мережі міськради або через VPN, журнал входів.
- **ДЕМО-дані позначені** в інтерфейсі й у API (`"demo": true`), щоб їх не сприйняли за факт.
- **Генератори не показуються.** Рішення не містить і не публікує даних про генератори реальних закладів; автотест у `backend/tests/test_solar.py` перевіряє, що в API СЕС немає слів «генератор» і «резервн».
- **Без ПІБ і телефонів.** Сирий «Інформація щодо впровадження СЕМ…xlsx» містить ПІБ і телефони — його немає в репозиторії (`.gitignore`), рішення його не використовує. Сирий `Лічильники.xlsx` (заводські номери) також виключено.
- **Жодних ключів у репозиторії.** Налаштування — у `.env` за зразком [.env.example](.env.example). PVGIS і Open-Meteo працюють без ключа.
- Пропуск у даних — це «немає даних», а не нуль: валідатор позначає, а не виправляє мовчки. Воєнні відключення не вважаються аномалією.
- **Клас A–G — не офіційний енергосертифікат.** Рекомендації СЕС — не проєкт станції.

## 9. Відомі обмеження

- **2026 рік неповний** (до 11.11.2026, ~86 % року). Базовий рік — 2025.
- **Даних про наявні СЕС, інвертори, акумулятори й приєднану потужність у пакеті немає** → модулі моніторингу й енергонезалежності працюють на ДЕМО-даних.
- **Помісячного споживання немає** (лише річні суми) → сезонний і добовий профілі — припущення за категорією.
- **Координати є лише в 34 з 311 будівель** → PVGIS рахується для центру Полтави; карти немає.
- **Тариф і вартість монтажу — припущення**; користувач вводить власні.
- Історії UMUNI замало для погодного прогнозу споживання (з кінця 2024 р.; потрібно ≥ 3 роки).
- Реєстр лічильників (D2-04) не підключено.
